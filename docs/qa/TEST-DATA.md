# Синтетические данные и две независимые сессии

## Пользователи

После обновления staging-схемы открыть QA-приложение в двух отдельных профилях браузера: обычный профиль для User A, другой профиль/инкогнито для User B. Две вкладки одного профиля обычно разделяют Supabase-сессию и не подходят для проверки A/B.

Создать A и B через `/register` с двумя отдельными контролируемыми тестовыми почтовыми ящиками, подтвердить письма и войти. Альтернатива для подготовки данных — два пользователя с подтверждённым email в staging Dashboard → Authentication → Users. Во втором случае реальная регистрация/доставка ещё не проверены. Пароли выбрать разные, хранить в менеджере паролей; не записывать в коллекцию, Git или отчёт. Не использовать аккаунт владельца проекта и service-role в Postman.

Адреса вида `qa-a@example.test` использовать только как синтетические контакты в **резюме**. Они не получают почту; для регистрации взять реальные тестовые ящики под своим контролем. Supabase может ограничивать отправку писем: сверить SMTP/лимиты в staging Dashboard.

## Данные резюме

| Поле | User A | User B |
| --- | --- | --- |
| Название | QA-A — Frontend Demo | QA-B — Backend Demo |
| Имя | Алексей Тестовый | Борис Демонстрационный |
| Контактный email | qa-a@example.test | qa-b@example.test |
| Возраст | 25 | 28 |
| Навыки | JavaScript 4, React 3 | PostgreSQL 4, REST API 3 |
| Опыт | Example QA Lab, Frontend developer, 2024–2025 | Demo API Lab, Backend developer, 2023–2025 |
| Образование | Учебный университет, Информатика, 2020–2024 | Демонстрационный институт, ИТ, 2018–2022 |
| Ручной проект | Demo task board, React, https://example.test/task-board | Demo API, PostgreSQL, https://example.test/api |
| Фото | сгенерированная геометрическая картинка | другая синтетическая картинка |

Создать по одному основному документу и отдельный документ `QA-DELETE-ME` для удаления. Записать локально UUID пользователей, UUID резюме A/B и текущие revision — это разные значения. Отдельно подготовить пустое резюме, длинные тексты и копию для конфликта двух вкладок **одного** пользователя.

Не импортировать production-данные. Для AI использовать только эти вымышленные описания. Для GitHub import публичные репозитории не считать синтетическими персональными данными: выбрать собственный специально созданный demo-аккаунт; без этого интеграцию оставить отдельной зависимостью.

## Postman

Импортировать collection из этого каталога. В локальном environment задать `supabase_url`, `anon_key`, `access_token`, `refresh_token`, `email`, `password`, `user_id`, `resume_id`, `revision`, `qa_origin`. Значения токенов/паролей хранить в Postman Vault или локально без синхронизации/экспорта. В коллекции нет скриптов, Runner не нужен: запросы отправлять вручную, значения из ответов переносить вручную.

`resume_id` заранее создать как новый UUID локально (`[guid]::NewGuid()` в PowerShell), сохранить его до первого create и повторять только для проверки идемпотентности. На новый документ брать новый UUID. После save копировать новый `out_revision`; устаревший revision нужен только для сценария конфликта. POST create не обновляет существующий документ.

Для A/B иметь два отдельных локальных Postman environment. В запросе с токеном B подставить UUID документа A и наоборот. HTTP 200 с пустым массивом для SELECT чужих строк может быть нормальным результатом RLS, а не разрешённым доступом. При PATCH/DELETE проверить возвращённые строки и повторно прочитать документ владельцем. Запрос без Bearer или с anon key вместо пользовательского JWT не проверяет изоляцию авторизованных пользователей.

Очистка: удалить только собственные `QA-*` резюме через UI/REST. Проверить каскад в дочерних таблицах. Файлы старых аватаров очищать отдельно и только в своём staging-префиксе; удаления профиля/Storage при удалении резюме не обещаются. Удаление тестовых Auth-пользователей — отдельное действие администратора staging после завершения работы.

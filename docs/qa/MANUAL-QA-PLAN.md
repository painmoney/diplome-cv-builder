# План самостоятельного Manual QA

Это последовательность проектирования и выполнения будущих проверок, без готовых статусов, тестовых прогонов или баг-репортов. P0 — блокирует доступ/данные/изоляцию; P1 — основной сценарий; P2 — дополнительные функции. Начинать после выравнивания staging-схемы. Инструменты: браузер/DevTools, Postman с ручной отправкой, Supabase Dashboard/SQL Editor либо PostgreSQL-клиент с read-only подключением.

| 2. CRUD резюме | P0: список, create, open, rename, duplicate, delete, прямые URL | потеря данных, чужой UUID, повтор create, каскад; копия делит данные/фото | 2 основных и disposable-документы, UI, RPC, SQL read-only |

| 9. Изоляция пользователей | P0: A→B и B→A через UI, REST SELECT/INSERT/PATCH/DELETE, обе RPC и Storage | отсутствие WHERE в клиенте не должно раскрыть данные; permissive policy, owner SQL обходит RLS | разные пользовательские JWT и браузерные профили; Postman, повторное чтение владельцем, SQL только как дополнительное свидетельство |
| 10. Ошибки/интеграции | P1: offline/slow/reconnect, неверный путь, несуществующий UUID, ошибка сохранения; P2: AI/GitHub | ложное «сохранено», необработанные ошибки, бесконечный spinner, отправка реальных данных | disposable-данные, DevTools Console/Network, GitHub demo-аккаунт, Puter по готовности, сценарии отсутствующего токена/отказа согласия |

Для изоляции не ограничиваться SELECT: проверить, что попытка B изменить/удалить документ A не меняет данные при последующем чтении A. Аналогично проверять подмену user_id/resume_id при INSERT и UPDATE. Для RPC проверять UUID чужого документа и повтор создания с ним. Конфликт revision — сценарий двух вкладок **одного пользователя**, а не двух разных аккаунтов. Публичное чтение фото не считать нарушением RLS.

При чтении БД учитывать, что дочерние строки пересоздаются, профиль аккаунта отделён от документа, JSON содержит больше полей, чем SQL-проекции. Для проверки rollback при ошибке RPC использовать только специально созданный документ и ручной запрос, затем сверять исходное состояние владельцем.

Перед началом зафиксировать URL, commit, браузер/ОС, staging ref, актуальность схемы и доступность внешних сервисов. Фактические результаты, доказательства и дефекты оформляются автором при самостоятельном выполнении; этот план их не предопределяет. Не включать в портфолио токены, пароли, реальные персональные данные или результаты проверки production.

## Подтверждено технически

- Сборка staging создаёт `dist`. ESLint: 0 ошибок / 17 существующих предупреждений. Safety scan проходит. Автотесты не добавлялись, не менялись и не запускались вручную; существующий CI запускается при PR.
- В живой БД 15 миграций; последние две — SQL существующих миграций Storage/аватара. [Точное соответствие версий](APPLIED-MIGRATIONS.md).
- `profiles.avatar_shape` существует: text NOT NULL, default round, CHECK round/square.
- RLS включён на семи таблицах; 28 public-политик владения, четыре Storage policies. Обе resume RPC — SECURITY INVOKER с пустым search_path. Проверены FK CASCADE дочерних таблиц.
- Два синтетических аккаунта подготовлены через административную генерацию signup-ссылок без отправки писем. Email-токены подтверждены публичным Auth API; парольный вход, восстановление сессии в новом клиенте и logout работают. Refresh token после logout отклонён.
- Пользовательские create/save RPC создают/сохраняют резюме, profile upsert принимает avatar_shape; новый клиент читает изменённые данные и revision=2. Устаревшая revision возвращает P1005.
- В обоих направлениях A→B/B→A: чтение чужого резюме возвращает []; save RPC — P1004; REST PATCH/DELETE не меняют строк; вставка skills в чужой документ отклонена с 42501. Последующее чтение владельцем подтверждает сохранность документа.
- Создан и удалён отдельный disposable-документ, дочерние skills после удаления отсутствуют. Основные синтетические документы A/B оставлены для технической проверки UI.
- Storage: загрузка своей синтетической PNG работает; B не может загрузить/удалить объект в папке A. Публичный GET возвращает 200; владелец удаляет свой объект. Bucket avatars: public, 5 MiB, jpeg/png/webp/gif.
- `github-repos` обновлён исходниками этой QA-ветки с сохранением verify_jwt=true. Запрос без пользователя — 401, с пользователем — контролируемая 503 GITHUB_TOKEN_NOT_CONFIGURED. Реальный импорт пока недоступен.

## Ограничения

Доставка signup/recovery-писем в реальный почтовый ящик не проверена: административная генерация и проверка токена не заменяют SMTP/email-поток. OAuth-провайдеры staging отключены. AI/Puter и экспорт файлов не проверялись в этой технической API-проверке. GitHub import требует серверный GITHUB_TOKEN в staging Function Secrets. Security advisor сообщает об отключённой защите от утёкших паролей; RLS-предупреждений нет. В унаследованной схеме profiles не имеет FK к auth.users; новая связь не добавлялась вне задачи запуска.

Полный браузерный сценарий на QA-домене и Auth redirect-конфигурация имеют отдельное подтверждение в DEPLOYMENT.md. Проверки SDK/API выше не обозначаются как UI-проверки.

## Изменения конфигурации

Guard читает эффективные значения Vite, проверяет точный staging hostname, запрещает серверные ключи в клиентской настройке и ошибочную роль/ref legacy JWT. Автоматическая публикация VITE_* отключена через envPrefix: []; Vite явно включает только Supabase URL, публичный клиентский ключ и необязательный Sentry DSN. Служебные VITE_* от хостинга не блокируют сборку и не попадают в bundle. Это проверено сборкой с отдельной контрольной переменной. Publishable key выбран из staging через подключение Supabase.

Добавлены env-шаблон и отдельный Vercel CLI-конфиг. Dev staging использует loopback/fixed port. Safe packaging и filename scan разрешают только известные env-шаблоны; реальные env-файлы/ключи не публикуются. Бизнес-логика и существующие автотесты не изменялись.

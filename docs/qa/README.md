## Текущая готовность

Локальный frontend запускается на `http://127.0.0.1:5199` и использует существующий staging `jerwfvhpoanoukxiyvwq`. Публичного Vercel-развёртывания в рамках подготовки нет. Критерий полной готовности пока **не достигнут**: живая схема staging отстаёт от frontend, требуется применить проверенные миграции и выполнить сценарии с двумя пользовательскими сессиями.

Подтверждено техническими проверками:

- `npm ci` установил 471 пакет по lockfile; `npm run build:staging` создал `dist`.
- `npm run lint`: 0 ошибок, 17 существующих предупреждений. `npm run safety:scan`: PASS, 19 файлов.
- Главная страница и форма регистрации отображаются в браузере. Перезагрузка `/register` работает; прямой переход `/dashboard` без сессии переводит на `/login`.
- Публичные Auth settings staging: email включён, signup разрешён, подтверждение email требуется; все OAuth-провайдеры выключены.
- Анонимный GET к `resumes` отклонён с HTTP 401. Это не доказательство изоляции двух авторизованных пользователей.
- По read-only OpenAPI staging доступны семь ожидаемых таблиц и обе RPC. В `profiles` **нет `avatar_shape`**. Текущий клиент выбирает и сохраняет этот столбец: необходима миграция `20260807000000_add_avatar_shape.sql`.
- Bucket `avatars` существует, public=true, лимит 5 MiB, MIME: webp/png/jpeg. В миграции дополнительно предусмотрен gif; история её применения и фактические policies не подтверждены.
- В dev-консоли есть предупреждения React Router о v7 и React о передаче `whileHover` в DOM на главной. Падения открытых публичных страниц не наблюдались; это не заключение обо всём приложении.

Не подтверждены запуском: регистрация с подтверждением email, вход, CRUD резюме, сохранение после reload, RLS A/B, экспорт файлов, AI, GitHub import, миграционная история, SQL-каталог, Auth Site URL/allowlist живого проекта. Автотесты не создавались и не запускались вручную; существующий GitHub CI запускается автоматически при PR.

## Что изменено

Проверки frontend-окружения теперь читают эффективные значения по правилам Vite, включая переменные хостинга. Они сверяют точный staging hostname с существующим реестром, запрещают серверные ключи, проверяют роль/ref legacy JWT и не требуют файла primary. Publishable key проверяется по формату; его связь с проектом необходимо подтвердить запросом к staging. Режим staging также защищён при прямом запуске Vite. Неизвестные `VITE_` переменные блокируются, чтобы случайный секрет не попал в клиент.

Добавлены публичный шаблон `.env.staging.example` и отдельный `vercel.staging.json`. Команда dev использует loopback и фиксированный порт: при занятом порте она останавливается, чтобы Auth redirect не оказался на другом origin. Safe packaging и CI-проверка имён файлов разрешают только два известных env-шаблона; реальные `.env` по-прежнему запрещены. Восстановлен отсутствовавший `AGENTS.md` с действующими правилами удалённого доступа Supabase: на его наличие ссылаются существующие safety checks. `.vercel/` исключён из Git. Бизнес-логика, RLS, SQL-миграции и существующие автотесты не изменялись; удалённые данные не изменялись.
